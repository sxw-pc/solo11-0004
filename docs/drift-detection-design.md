# 站点结构漂移探测与脚本修复建议——设计方案（只含方案与取舍，不含实现代码）

## 0. 问题界定与设计原则

机器人在已授权站点上跑 YAML 动作脚本，站点改版的三种典型形态对应三类故障：

| 改版形态 | 现状报错点 | 本质 |
| --- | --- | --- |
| label 改名（"用电量（千瓦时）"→"季度用电量"） | `resolve_control` 抛 `label not found`（SCRIPT 类） | 语义不变、锚点失效 |
| 表单拆步/顺序调整（第二步字段挪到第三步） | 步骤在错误页面上找不到控件 | 流程拓扑变化 |
| 新增必填项（新增"联系电话"且服务端校验非空） | 提交被服务端拒绝，或页面出现脚本未知控件 | 契约变化，机器人无值可填 |

本方案要新增的是一个**离线、只读、确定性的诊断组件**（下称 drift-detector），它消费失败链路已有的脱敏证据，产出分级报告与 YAML 补丁**建议**。四条不可动摇的原则：

1. **只建议，不执行**：补丁永不自动应用，必须先过现有离线 `validate`，再由人工采纳。
2. **宁可停机不可猜值**：涉及"机器人不知道填什么"的契约变化，一律高危上报，禁止用推断值继续写入。这与仓库"宁可在提交前失败，也不在不确定状态下重复写入"的定位一致。
3. **结构与数据分离**：下拉选项等可枚举动态数据的自然更替不是漂移，不得污染报告。
4. **确定性可复现**：同一份证据 + 同一份基线 + 同一版本算法，任何时间、任何机器产出字节级一致的报告。

## 1. 系统挂点：失败链路与证据存储中的位置

### 1.1 现有链路回顾（基于当前代码事实）

```text
DSLExecutor._run_step
  └─ handler → resolve_control / resolve_clickable
        └─ ScriptError(SCRIPT 类, 不可重试)
              └─ engine.execute 捕获 → _record → snapshot_cb 落盘脱敏 HTML
                    └─ EvidenceStore: <evidence>/<run>/<task>/step-NN.html + actions.jsonl
                          └─ task 置 FAILED → ledger(steps 表记录 error_class/error)
```

关键事实，决定了挂点设计：

- 选择器/label 失败是 `ErrorClass.SCRIPT`，天然不进重试（`RETRYABLE_CLASSES` 只含 NETWORK/SERVER），不会被退避重试掩盖。
- `_safe_page` 保证失败时保留当前页，`sanitize_html` 已对 password/token 类控件和已知密钥串脱敏——drift-detector **只能读脱敏后的产物，不允许接触原始响应**。
- schema（`validate_script`）严格拒绝未知顶层键和未知步骤参数，所以任何新元数据必须显式扩 schema，不能靠注释或旁路文件偷偷塞进脚本。

### 1.2 挂点设计：失败后旁路，不在执行热路径上

**采纳方案：失败后异步旁路触发，detector 是独立子命令/独立阶段，不嵌入 engine。**

- 触发条件：ledger 中某 task 的失败步骤 `error_class = SCRIPT` 且错误信息属于定位类（`selector not found` / `label not found` / `ambiguous label` / `label has no associated control`），或者失败页快照中出现脚本未引用的可填写控件（探测性发现，见 §3.4）。
- 输入只有三样：① 该 task 失败步的脱敏 `step-NN.html`（必要时含同 task 前序步快照以还原流程位置）；② 当前脚本 YAML；③ 基线（见 §2）。
- 输出落到证据目录旁的新子目录 `<evidence>/<run>/<task>/drift/`：`report.json`（机读）、`report.md`（人读）、`patch-suggestions.yaml`（补丁建议），并在 ledger 的 steps 表增加一个可空关联字段指向报告 id；task 状态机**不新增状态**，FAILED 仍是终态，报告只是 FAILED 的附属诊断。
- 也支持手工对任意历史证据目录重跑（`detect --evidence <path> --script <path>`），用于复盘和算法回归。

**取舍与被否方案：**

- **被否 A：在 engine 的 `_run_step` 里同步内联探测。** 理由：①把诊断复杂度塞进写入热路径，一次定位失败要多做整页解析，拖长失败时长；②detector 出 bug 会二次污染本就失败的任务；③违反单一职责，且无法对历史证据重放。旁路触发让 detector 崩溃只影响报告产出，不影响既有失败语义。
- **被否 B：定时主动爬站点做健康巡检（无失败也探测）。** 理由：机器人定位是"写"不是"采"，主动抓取授权站点的非任务页面在合规上越界，且无头 requests+BeautifulSoup 无法稳定复现需要会话状态的多步表单，巡检拿到的页面可能与真实填报路径不同，产生大量伪漂移。主动探测只保留一个**受限例外**：在一次成功运行结束后，对实际经过的页面顺带做指纹比对（见 §2.2 的成功即刷新基线），不额外发请求。
- **被否 C：新增 DRIFT_SUSPECTED 任务状态。** 理由：现有状态机的 FAILED 已准确表达"未写入、需人工介入"，新状态破坏 `plan_resume` 的续跑集合判定（success/skipped 之外都要重跑），还要改 CLI、报表、测试一片。报告作为 FAILED 的附件即可，状态语义不膨胀。

### 1.3 与脚本 schema 的耦合方式

**采纳方案：脚本保持纯净，新增一个与脚本同 stem、同目录的旁路"期望清单"文件（如 `quarterly_report.expectations.yaml`），由显式的 schema 版本管理；脚本内零侵入。**

- 期望清单按步骤索引声明每个定位步骤的**结构化期望**：控件类型（input/select/textarea/checkbox）、name/id、归一化 label、是否必填、所属表单 id、在表单内的序号、该步所在流程页的锚文本（对应现有 `assert_text` 的"第 N 步"标题）。
- 为什么不直接从脚本反推全部期望：脚本只有 `selector` 或 `label` 一个锚点，拿不到控件类型、必填性、序号这些"画像"信息；而这些恰恰是打分（§3）和高危判定（§4）的输入。
- 期望清单由 detector 在每次**成功运行**后基于证据自动生成/刷新**草案**，人工 review 后定稿入库——它是受控工件，不是临时产物。

**取舍与被否方案：**

- **被否 A：把期望元数据以新键（如 `expect:`）写进每个 step。** 理由：①`schema.py` 的 `COMMON_KEYS`/`ACTION_REGISTRY` 是闭合白名单，加键要动动作注册表、参数校验、`Step` dataclass、全部 fixture；②脚本的职责是"怎么操作"，期望是"站点长什么样"，两者变化频率不同（站点改版先动期望、后动脚本），绑在一起改一个就要碰另一个，diff 噪声大；③现有脚本同时混有 selector 派和 label 派，内联期望会让两种风格的步骤都膨胀。旁路文件让脚本 schema 保持 v1 不动。
- **被否 B：不要期望清单，全部从脚本 + 成功快照现场推断。** 理由：推断结果不稳定（快照里有啥算啥），无法表达"这个字段本来就该存在"的契约语义，新增必填字段的高危判定（§4.3）将失去参照系——没有"期望集合"就无法定义"多出的必填项"。
- **被否 C：期望清单放进站点画像统一管理（见 §2 的三选一讨论）。** 部分采纳但分层：期望清单是**脚本视角**（按 step 索引、随脚本版本走），站点画像是**页面视角**（按 URL/表单走、跨脚本共享），二者粒度和生命周期不同，合并会让单脚本的变更牵动全局画像。

## 2. 取舍一：比对基线选什么

三种候选基线各有盲区，结论是**分层基线、以"上次成功运行的证据快照"为主锚，脚本期望清单为契约层，独立站点画像为可选共享层；任何一层缺失都有明确退化路径，绝不因为基线缺失而跳过诊断或放行写入。**

### 2.1 三个候选的正面权衡

| 维度 | A. 上次成功运行的证据快照 | B. 脚本声明的定位器期望（期望清单） | C. 单独维护的站点画像 |
| --- | --- | --- | --- |
| 时效性 | **最高**：成功一次即刷新，天然带时间戳 | 中：随脚本发布走，两次改版之间是静态的 | 最低：靠人工/专项流程维护，最容易腐烂 |
| 含信息量 | 高：真实 HTML 含完整 DOM、name、类型、必填、选项 | 中：只含脚本作者意识到的字段，未引用控件不可见 | 最高：可覆盖整页所有控件、跨脚本共享 |
| 误报率 | 低-中：真实对真实，但会把"当次成功时的临时状态"误当成结构（如 A/B 实验页） | 低：声明即契约，差异即异常，但期望本身过期时误报升高 | 维护良好时最低；一旦腐烂，误报与漏报双高 |
| 维护成本 | **近乎零**：复用现有证据落盘，成功即产出 | 中：需要 schema、review 流程，但可自动出草案 | **最高**：需要独立工件、owner、评审节奏 |
| 抗"静默语义漂移" | 弱：两次快照都对，不代表字段没被张冠李戴 | 强：契约明确，label 改名立刻显形 | 强 |
| 首次运行/冷启动 | 不存在（无历史成功） | 随脚本自带，**冷启动唯一可用** | 取决于是否预先建设 |
| 与现有架构契合 | 直接复用 `EvidenceStore`，零新存储 | 需要新增期望清单工件（§1.3） | 需要全新存储与治理 |

### 2.2 采纳的分层结构与刷新策略

1. **主锚——成功证据指纹（L1）**：不是存整页 HTML 当基线（整页包含动态数据，比对必噪），而是从最近一次成功运行的脱敏快照中抽取**结构指纹**：每个表单的 `(form_id, 控件序列)`，每个控件的 `(稳定标识, 控件类型, 必填标志, 归一化 label, 表单位点)`，其中稳定标识按 `name > id > aria-label > label 文本` 的优先级取。指纹按 `(脚本名, 脚本版本, 步骤号)` 归档，带成功运行的 run_id 与时间戳。**成功运行结束时自动刷新 L1 草案并替换旧指纹**——这是 §1.2 被否 B 里保留的唯一"主动"动作，因为不发新请求、只处理已经拿到的页面。
2. **契约层——期望清单（L2）**：§1.3 的旁路文件，进入版本库，随脚本变更走评审。它定义"哪些字段必须存在、什么类型、是否必填"，是高危判定的唯一契约依据。
3. **共享层——站点画像（L3，可选）**：仅当多个脚本共用同一站点、且团队愿意承担 owner 成本时才建。页面视角，按 URL/表单 id 组织，用于跨脚本复用 label 同义词表和字段类型知识（例如"联系电话"在全站长什么样），**不参与单任务的自动停机判定**，只作为打分（§3）的先验知识源。

比对顺序：失败快照先对 L1 做结构 diff（回答"页面相对上次成功变了什么"），再用 L2 做契约判定（回答"变化是否破坏了脚本契约/是否出现契约外必填项"），L3 仅在匹配打分阶段提供先验，不单独触发告警。

### 2.3 基线缺失或过期的退化策略

定义指纹 TTL（可配置，建议默认 30 天）与"代差"概念（当前站点结构与 L1 之间隔了几次未观测改版无法知道，但可以知道 L1 的年龄）。

| 情形 | 退化行为 |
| --- | --- |
| L1 缺失（首次运行、证据被保留策略清理、`keep_runs` 淘汰） | 降级为 L2 单基线：只做契约校验和失败页内部分析（未知控件扫描、label 模糊匹配），报告标注 `baseline=L2_ONLY`，所有自动补丁建议的置信度上限压到 §3.5 的"人工确认档"，禁止产出自动档建议 |
| L1 过期（超 TTL） | 仍可做 diff，但报告对 diff 结论打 `STALE_BASELINE` 标记，漂移等级不得低于 P2（§4），即"陈旧基线下的低危结论也要人工看一眼"；成功一次后 TTL 自动重置 |
| L2 缺失（老脚本没有期望清单） | 首次成功运行后自动生成期望清单草案；草案定稿前，新增必填项检测退化为"失败页相对 L1 的新增控件 + HTML 必填属性/服务端错误文本"的启发式，命中即直接 P1 高危，不做低判 |
| L1、L2 都缺（纯冷启动） | 不做漂移定性，只输出**事实型报告**：失败步骤、错误原文、失败页上全部可填写控件的清单（脱敏）。明确告知"无基线，无法判断是否改版"，由人工建立基线。**绝不允许在无基线时猜测性产出补丁** |
| L3 缺失 | 无影响，打分回落到只用页内证据（§3 权重归一化时去掉画像先验项） |

### 2.4 被否的反面方案

- **被否 A：只用 L1（成功快照），不要期望层。** 理由：快照只能表达"上次长这样"，无法表达"必须有什么"。新增必填字段在第一次失败时，L1 diff 能发现多了控件，却无法断定它是必填还是可选、是否阻塞提交——必填性来自服务端校验（如 `forms_def.validate_step*` 里的"不能为空"），HTML 属性未必可靠。没有契约层就只能猜，违背不猜值原则。
- **被否 B：只用 L2（脚本期望），成功快照仅作证据不做基线。** 理由：期望清单天然滞后且只覆盖脚本引用的字段；纯样式调整、字段顺序变化、未引用控件的新增对 L2 不可见，漏报率高。而顺序调整恰是最适合自动出补丁的低危场景（§4.2），丢掉 L1 等于丢掉自动修复的主要适用面。
- **被否 C：以 L3 站点画像为唯一基线，集中治理。** 理由：维护成本与腐烂风险最高，画像 owner 一旦断档，全站点机器人同时失去基线；且画像与具体脚本版本解耦后，无法回答"这次改版是否破坏了**这个脚本**"，告警粒度对不上修复动作。本方案把 L3 降为可选先验源，正是为了隔离它的腐烂半径。
- **被否 D：基线存原始 HTML 全文而不是结构指纹。** 理由：原始 HTML 含 token、隐藏域、随机 nonce、动态选项，全文 diff 每次运行都不同，报告被噪声淹没（与 §5 的动态降噪目标直接冲突）；指纹只保留结构维度，天然过滤数据层变化。

## 3. 取舍二：旧字段到新候选的打分与防错配

当 L1 diff 发现基线里的某控件在失败页找不到原样锚点时，进入候选匹配：在失败页全部可填写控件中为它找新身份。

### 3.1 特征与权重（总分 100）

| 特征 | 权重 | 打分要点 |
| --- | --- | --- |
| **name 属性稳定标识匹配** | 35 | name 完全相同给满分；仅大小写/连字符下划线差异给 60%；无 name 或不同为 0。name 是表单提交的实际键，服务端契约通常锚定它，改版中比 label 和 CSS 类名稳定得多 |
| **label 文本相似度** | 30 | 归一化（去空白、去括号单位、全半角统一、去标点）后：完全相同满分；包含关系/子串 70%；分词后 token Jaccard 或编辑距离归一化按比例给分。同义词表（来自 L3 或人工维护的小型白名单，如"用工人数≈期末从业人数"）命中按 85% 计 |
| **字段类型与必填性一致** | 20 | 控件类型（text/number/select/checkbox/textarea/date/file）一致给 12 分；必填标志一致再给 8 分。类型从 input type、tag name、select/textarea 区分；必填从 `required` 属性、label 的 `*` 标记、服务端错误文本三源印证，三源矛盾时该项只给一半并标注证据冲突 |
| **DOM 位置/结构邻接** | 15 | 同表单 id 给 8 分；在表单内序号差 ≤2 给 4 分；相邻控件集合（前后兄弟的 label 集合）重合给 3 分。拆步场景下同表单 id 会失效，此时邻接分改按"流程页锚文本 + 页内序号"计，并把该 8 分的缺失显式记录为拆步信号（喂给 §4 的分级） |

设计理由：name 权重最高因为它最接近服务端契约；label 次之因为这正是最常改的东西，不能让最易变的特征主导；位置只给 15 因为拆步/重排会让位置整体失效，高权重位置分在改版时反而制造误配；类型必填作为"一票否决型"硬约束的软化版（见 3.3）。

### 3.2 "联系电话/联系地址"类高相似 label 的防错配

这是本方案最危险的失配模式：两个 label 共享前缀、同属文本输入、常常相邻（联系电话、联系地址、联系人；用电、用水、用气）。四道防线：

1. **硬约束前置（类型不兼容一票否决）**：checkbox 候选不参与 text 字段的匹配，file 不匹配 fill，number/date 的输入约束不匹配时直接剔除候选，不进入加权。语义类型标签（电话类看 inputmode/tel、pattern、maxlength；地址类看 textarea 或长文本 maxlength）作为子类型再过滤一层。
2. **区分性子串强制核对**：对归一化后仍存在公共前缀的 label 簇，匹配必须验证**差异 token**（"电话"vs"地址"vs"人"），差异 token 不一致时 label 项封顶 40% 分（即 12/30），使总分天花板落在 35+12+20+15=82，进不了 3.5 的自动档。"用电/用水/用气"同理，差异字（电/水/气）是强制核对点。
3. **name 锚定优先且 name 冲突时不允许纯 label 翻盘**：若两个旧字段的 name 各自存在于新页，label 再像也只能按 name 配对；反过来，name 缺失时 label 相似候选的总分上限同样压到人工档。即**禁止"label 像但 name 对不上"的组合自动晋级**。
4. **互斥分配（一对一双向匹配）**：所有旧字段与候选先算完整得分矩阵，再做全局最优指派（带权二分图匹配），保证两个旧字段不会抢到同一个新控件、一个新控件也不会被复用两次。"联系电话"和"联系地址"即使单项分数接近，全局指派会让它们各归其位；指派后若某配对低于阈值，双双转人工而不是各自取局部最高。

### 3.3 置信度阈值与处置

| 总分区间 | 判定 | 处置 |
| --- | --- | --- |
| ≥ 85 且通过 3.2 全部硬约束、且为全局指派唯一最优 | **高置信** | 允许进入 P3 自动补丁建议档（§4.2），报告仍逐条列出打分明细供复核 |
| 70–84 | **中置信** | 只进报告的"候选建议"，补丁文件里标 `confidence: medium`，采纳前必须人工确认；离线校验照跑但不改变人工门槛 |
| 50–69 | **低置信** | 不给补丁，只列候选与得分，供人工排查 |
| < 50 或无候选 | **未匹配** | 判定为字段移除/无法定位，按 §4 分级上报；不允许"选个最像的" |

**并列候选处置（明确规则，杜绝任意性）：**

- 分差 ≤5 分视为并列，**一律不取 Top1**，整体降一档处置（高置信并列降为中置信人工档），并在报告中并排列出双方的特征对比表。
- 并列且涉及 3.2 的高相似 label 簇：直接判 P2 人工，不允许任何自动档。
- 全局指派后出现"旧字段 A 的首选是候选 x，但 x 同时是 B 的更高分配"这类冲突：以全局指派结果为准，被抢走首选的 A 拿次优候选并强制降档。

### 3.4 反向发现：脚本未知的新控件

匹配不只处理"旧的找不到"，还要扫描失败页上**脚本步骤未引用、L1 指纹中也不存在**的控件：

- 新控件带必填标志（三源印证，见 3.1）→ 直接进 §4.3 的 P1 通道，这是"新增必填项"的主检测路径，不依赖提交被拒才发现。
- 新控件可选 → P4 提示级，不阻塞。
- 新控件是 select 且选项集合变化 → 交 §5 的动态数据通道处理，默认不算漂移。

### 3.5 被否的反面方案

- **被否 A：label 相似度一票主导（权重 ≥60%）。** 理由：label 恰是改版中最不稳定、也是"联系电话/联系地址"失配的根源；高 label 权重会把改名当漂移、把近名标签错配，误报误配双高。name 主导（35%）+ 硬约束 + 全局指派才能压住。
- **被否 B：用嵌入模型/LLM 做语义匹配代替规则打分。** 理由：①违反确定性可复现原则，模型版本、采样、环境变化都会让同一份证据产出不同报告，无法审计、无法回归；②语义模型对"电话/地址"这类近义短文本的区分度没有保障，且无法给出可向审计解释的逐项得分；③离线/内网部署与数据外发合规风险。本方案全部采用可解释的规则特征，同义词表是唯一人工知识入口且本身受控。
- **被否 C：DOM 位置高权重（≥40%），按"第几个输入框"配对。** 理由：拆步和重排正是三大改版形态之一，位置在改版时系统性失效，高权重位置分会把一次重排放大成全字段错配。位置只保留 15% 的辅助分。
- **被否 D：逐字段独立取最高分，不做全局指派。** 理由：必然出现两个旧字段抢同一新控件的情况，高相似 label 簇下几乎必错；双向匹配把局部贪心换成全局最优，代价只是计算量，对表单规模（几十个控件）可忽略。
- **被否 E：阈值固定一刀切且并列取字典序/第一个。** 理由：并列取 Top1 是把随机当确定；分档 + 并列降档 + 人工兜底让每条建议的可信度可预期。

## 4. 取舍三：漂移分级与自动/人工边界

### 4.1 四级模型

| 级别 | 定义 | 典型场景 | 处置 |
| --- | --- | --- | --- |
| **P1 高危·停机上报** | 机器人缺少继续所需信息，或变化触及提交契约 | 新增必填字段且任务 payload 无对应值；字段类型根本变化（text→文件上传）；表单多出无法跳过的确认/授权控件；流程出现脚本未知的新步骤页且位于 final 提交之前；服务端校验规则收紧（错误文本显示新的非空/格式要求） | task 保持 FAILED，输出高危报告与**信息缺口清单**（需要什么值、证据原文、建议在任务清单/期望清单里补什么），禁止任何补丁自动档，人工补齐数据与脚本后走完整离线校验 + dry-run |
| **P2 中危·人工确认补丁** | 结构可定位但存在歧义，自动修复有失配风险 | 中置信匹配（70–84）；并列候选；高相似 label 簇的重命名；拆步导致步骤归属变化（字段还在但换了页面/表单）；`ambiguous label`（一个 label 现在匹配多个控件） | 产出补丁建议但锁 `confidence: medium`，报告附打分对比，人工逐条采纳 |
| **P3 低危·自动产出补丁建议（仍不自动应用）** | 高置信、纯机械、语义无损的变化 | label 改名且 name/类型/必填/邻接全部吻合（≥85 分）；字段顺序调整（控件集合不变、仅序号变化）；纯 CSS 选择器失效但 label 通道仍唯一命中；容器 id/class 样式改版 | 自动生成 YAML 补丁建议，可直接进入离线校验队列；**"自动"仅指生成建议，应用永远是人工动作（§6.1）** |
| **P4 提示·仅记录** | 不影响填报的差异 | 可选字段新增/移除；帮助文本、占位符、排版变化；动态数据变化（§5） | 进报告附录，不计入漂移计数，不告警 |

### 4.2 自动与人工的边界判定原则

边界划在**"信息是否充分"和"错误后果是否可逆"**两条线上：

- P3 自动档的充要条件：变化是**同构映射**（旧控件与新控件一对一、类型/必填/name 一致、分值 ≥85、无并列、不涉高相似簇），补丁只改"怎么找"（locator），不碰"填什么"（value 来源、payload 字段）。
- 一旦需要决定**值**——新增必填项填什么、新勾选项是否同意、未知步骤页怎么过——立即归 P1。机器人的任务清单（intake payload）是值的唯一合法来源，payload 里没有的键，detector 无权发明。
- 一旦映射**不是同构**（一对多、多对一、类型变化、跨步骤页迁移），归 P2。
- 位置顺序变化单独享 P3：控件集合指纹完全相同、仅顺序不同，对现有"按 locator 定位而非按序号定位"的脚本语义无损，补丁最多调整步骤排列或无需改脚本，只出说明。

### 4.3 新增必填字段为何必须停机（而不是猜值继续）

- 填报是**写入**，错误值的代价是对外提交了错误数据，且对方系统未必允许更正；这与采集场景"猜错了重抓"有本质区别。
- 猜值的风险谱：保守空值 → 服务端拒绝（变成显性失败，还算安全）；貌似合理的值（用上季度数、用企业名填空、勾选"同意"）→ **静默写入错误数据**，是最坏情形。任何让机器人"先填个像的"的设计都被否决。
- P1 报告的产出不是一句"新增字段"，而是结构化缺口：字段 label/name/类型/必填证据（HTML 属性或服务端错误原文）、当前 payload 的可用键列表、若存在名称相近的 payload 键则给出**映射建议但默认不绑定**（例如新增"联系电话"而 payload 恰好有 `contact_phone` 未使用——建议人工确认绑定，不自动连线）。

### 4.4 被否的反面方案

- **被否 A：三级模型，把 P2/P3 合并为"自动建议 + 人工抽查"。** 理由：抽查机制下中置信补丁会批量堆积，没人逐条看，等于事实上的自动应用；四级分档让"必须逐条看"的集合（P2）保持小而明确，抽查变必查。
- **被否 B：P1 也允许"占位值 + 跳过该字段继续后续步骤"的降级运行。** 理由：多步表单的服务端校验在提交页才触发（参考 `forms_def` 的分步 validate），占位值会让前面步骤全绿、最终提交失败，留下半成品会话，还可能触发对方的重复提交/风控；而且"继续跑"会在证据里混入大量与漂移无关的后续失败，干扰诊断。失败在最早的信息缺口处，证据最干净。
- **被否 C：按改版频率动态调阈值（站点稳定时降低自动档分数线）。** 理由：阈值是安全边界不是性能旋钮，动态阈值使报告不可复现、不可审计，且"最近没改版"不代表下次改版温和；阈值只能随算法版本显式调整并记入报告元数据。
- **被否 D：把样式/顺序变化静默吞掉，不出报告。** 理由：即使脚本无需修改，静默处理会让站点改版对运维完全不可见，多次小改累积成大改时丢失演化轨迹；P4/P3 留痕保证审计链完整，只是不告警。
- **被否 E：拆步场景让 detector 自动重排步骤顺序生成新脚本。** 理由：步骤顺序与 `assert_text` 流程锚点、重试/final 语义耦合（`final` 只能在 click 上、dry-run 在 final 处停），自动重排可能破坏提交流程的安全性；拆步归 P2，人工确认后改。

## 5. 取舍四：动态降噪——可枚举动态数据与结构变化分离

### 5.1 双层模型：结构指纹 vs 数据指纹

从每个页面抽两类指纹，分开存储、分开比对：

- **结构指纹（漂移判定对象）**：控件的存在性、类型、name/id、必填性、label 语义、表单归属与拓扑；select 控件只记录"它是 select、name 是什么、是否 multiple"，**不记录选项内容**。
- **数据指纹（独立通道，默认不告警）**：select/radio 的选项集合（value 与可见文本）、默认值、隐藏域中的业务数据、表格行数等。选项集合做内容归一化（去空白、排序后）哈希，单独存时间序列。

判定规则：

1. 选项集合变化但 select 的结构指纹不变 → 记为**数据更新事件**，进数据指纹时间序列，报告 P4 附录，不产生漂移计数、不触发告警。季度更新（如季度选择框新增 2026-Q1）落在这一层，天然静音。
2. 选项变化同时伴随结构变化（select 变 radio、name 改变、新增 free-text "其他"输入框）→ 结构部分正常走 §4 分级；数据部分仍走数据通道，一份事件两层归因。
3. **唯一会升级的例外**：脚本 `select` 步骤要选的值（`value:` 参数）在新选项集合中消失。这不是"选项自然更新"而是"脚本契约的值域被破坏"，升 P2——因为它会直接导致选择失败，但补丁方向明确（人工确认新选项对应物），不需要新数据，故不定 P1。
4. 选项集合的比较按 value 优先、可见文本为辅：站点常只改显示文案不改提交 value，value 不变即视为同一选项，显示文案变化归数据层噪声。

### 5.2 其他噪声源的抑制

- 隐藏域 token/nonce/CSRF、时间戳、随机 id（形如 `input-8f3a2c`）：指纹阶段直接剔除或归一化为占位符，不进基线。
- 分页/表格行数、错误提示文案、广告与公告位：不属表单结构，指纹抽取范围限定在 `form` 内的可提交控件及其 label，页面对比不做整 DOM diff。
- A/B 实验导致的间歇性结构差异：L1 记录最近 N 次成功指纹（建议 N=3）而非单点，当前结构与任一历史指纹同构即视为未漂移；全部不同才报。N 太小抗不住实验，太大掩盖真实改版，3 是折中；N 次成功都同构后旧指纹滚动淘汰。

### 5.3 被否的反面方案

- **被否 A：把选项集合纳入结构指纹，变化即漂移。** 理由：季度更新每季度稳定触发误报，报告信噪比崩溃后运维会忽略所有告警，真正的 P1 被淹没——这正是现状痛点的翻版。
- **被否 B：完全忽略选项变化，连数据指纹时间序列都不存。** 理由：值域收缩（某选项被下线）是真实的契约风险信号，且 §5.1 第 3 条例外需要选项数据才能判定；全忽略会让 `select` 值失效类故障退回到手工对比。存而不警是平衡点。
- **被否 C：用 LLM 判断"这个变化算不算漂移"来降噪。** 理由：同 §3.5 被否 B，不确定性进入安全判定链，不可复现、不可审计；噪声抑制必须靠确定性的分层规则。
- **被否 D：对随机 id 做模糊相似匹配后保留在指纹里。** 理由：随机会话 id 每次都变，模糊匹配既贵又会偶发错配；直接在抽取层归一化/剔除，成本最低且零误报。
- **被否 E：数据更新事件也生成补丁建议（例如自动把新选项加进脚本值域）。** 理由：脚本里的 `select value` 是业务选择不是选项清单，自动改值等于替业务做决定；数据事件只记录，唯一的升级路径（值消失）也只到 P2 人工。

## 6. 取舍五：建议格式、离线验证与安全边界

### 6.1 补丁建议格式（YAML，数据工件而非可执行物）

`patch-suggestions.yaml` 的设计要点：

- **不发明新脚本格式**：补丁的每个 hunk 定位到 `steps[i]`，给出"定位器替换建议"这一种原子操作（旧定位器 → 新定位器，selector/label 二选一的约束沿用现有 schema），外加元数据块。不支持多操作复合补丁，避免机器生成大范围重写。
- 每条建议携带：漂移级别（P1–P4）、置信度（high/medium/low）、打分明细（§3 四项各自得分与证据）、基线来源与版本（L1 指纹 id/run_id/时间戳、L2 期望清单版本、算法版本）、涉及的证据文件相对路径（仅脱敏证据目录内）、可逆性说明。
- P1 条目不产生 locator hunk，只产生 `information_gap` 块：缺口字段、必填证据、payload 可用键、建议的人工动作清单。
- 补丁文件头部固定 `auto_apply: forbidden` 声明，任何工具链读取到该文件时默认只做校验和预览；不存在"应用补丁"的自动命令，采纳动作 = 人工编辑脚本 YAML 本身（或人工把 hunk 复制进脚本），让脚本变更天然走现有版本库评审流程。
- 报告（report.json/md）与补丁同目录、同 run 可追溯；report.md 是人读摘要，report.json 是机读全量，二者由同一次确定性运行生成。

### 6.2 离线验证门禁（复用现有能力，不新增信任链）

人工采纳前必须依次通过，全部离线、不触网：

1. **schema 校验**：改后的脚本过现有 `validate`（`validate_script` 闭合白名单天然挡住任何畸形补丁），期望清单过它自己的同风格 schema 校验。
2. **任务清单校验**：若 P1 缺口要求新增 payload 键，过 intake 的行级/字段校验，保证新键有来源、类型合规。
3. **指纹回演**：用**产生本次报告的同一份脱敏失败快照**作为静态页面，让 detector 的定位器解析逻辑（复用 `resolve_control`/`resolve_clickable` 的纯函数部分）对新定位器做离线解析，必须唯一命中目标控件；再对 L1 基线快照回演，确认新定位器不会在旧页面上命中错误控件（双向回归）。
4. **mock 站点 dry-run/全量 pytest**：仓库自带 mocksite 与 85% 覆盖率门槛，脚本变更在本地 mock 上跑 `run --dry-run` 与测试套；mocksite 的 chaos 注入可扩展结构漂移开关（label 改名、拆步、新增必填），让每类 P1–P3 都有确定性夹具回归。
5. 四步全绿才允许人工合入；任一失败，报告关联回原 drift 报告，闭环标注。

### 6.3 确定性与可复现

- 算法纯函数化：输入（证据文件 + 基线 + 期望清单 + 算法版本号）→ 输出，无网络、无时钟读取（时间戳只作为输入数据原样回显）、无随机数、无模型推理、无 dict 遍历顺序依赖（所有集合在比较前排序）。
- report.json 键排序、列表确定序（按步骤号、再按分数降序、并列按稳定标识字典序），整体可做字节级 diff；报告内嵌全部输入的哈希（证据文件、基线指纹、期望清单、算法版本），换任何一个输入哈希必须换报告。
- 回归方式：固定证据夹具 + 期望报告快照，算法升级时全量重放比对，意外 diff 即测试失败。
- 阈值、权重全部是版本化常量，不读运行时环境变量（与 chaos 配置严格区分），调权重 = 发算法新版本。

### 6.4 安全与敏感信息边界

- **数据源封闭**：detector 只挂载在 `EvidenceStore` 输出之后，只读 `sanitize_html` 的产物；现有脱敏（password/token 控件置 `***`、已知密钥串替换）之外，报告生成时再做一层输出脱敏：label/name 之外的文本截断、任何残留的 value 属性不落报告、附件内容永不读取。
- **最小化摘录**：报告引用页面证据时只引结构片段（控件标签、属性名、归一化 label），不引整页 HTML；证据路径用相对路径，报告可脱离原始证据分发，但分发版默认剥离证据引用只留结论。
- **无外发通道**：detector 不携带任何网络客户端代码，物理上无法把证据发出本机；报告落盘在既有证据目录的保留策略（`keep_runs`）覆盖范围内，随证据一起到期清理。
- **建议无授权能力**：补丁文件不接触站点、不携带凭据、不含任何 value 注入（只改 locator）；`auto_apply: forbidden` + 无应用命令 + 脚本库评审，三重保证"永不自动应用"。
- 授权边界不变：整个机制不新增对站点的请求类型，唯一的新读取是对本地证据文件的读取，合规面与现状一致。

### 6.5 被否的反面方案

- **被否 A：检测通过后自动改写脚本并热加载继续跑。** 理由：直接击穿"只建议不执行"底线；热加载绕过脚本评审与离线校验，且在失败会话上续跑违背断点续跑的状态机约束（FAILED 只能重新 RUNNING，重跑计划由 `plan_resume` 从 ledger 重建，不接受现场改脚本）。
- **被否 D（分级）见 §4.4；此处补**：被否"补丁携带自动填充值"——任何在补丁里写 value 的方案都被否，因为那等于让 detector 成为业务数据来源，越过任务清单的唯一数据源地位。
- **被否 B：在线校验（拿建议直连真实站点试定位）。** 理由：①对授权站点产生计划外请求，合规越界且可能触发风控；②在线结果依赖站点当下状态，不可复现，校验通过不代表稳定；③网络抖动会被误读成补丁无效。离线静态回演 + mock 回归已能覆盖定位正确性，真实站点验证只发生在人工采纳后的下一次正式填报（本就是计划内请求）。
- **被否 C：报告输出原始 HTML 片段方便人工对照。** 理由：脱敏后的 HTML 仍可能含业务数据（企业名称、编号等），报告的分发范围通常大于证据目录；只输出归一化结构摘录，把敏感面限制在受控的证据目录内。
- **被否 E：把 drift 报告写进 ledger SQLite 与运行台账混存。** 理由：台账是结构化运行记录、报表（summary.json/csv）直接消费它，混入大段诊断文本会膨胀数据库并改变报表口径；报告以文件工件形式留在证据目录，ledger 只存一个可空报告 id 做关联，存储职责清晰。
- **被否 F：告警推送（ webhook/邮件）直接发报告全文。** 理由：外发通道即敏感面；通知只含 run_id、task_id、漂移级别、报告 id 和"请在本机证据目录查看"的指引，内容永不出本机。

## 8. 落地顺序建议（演进路径，非并行大改）

1. **第一步（零侵入）**：结构指纹抽取 + L1 基线（成功运行自动产出）+ 失败触发的事实型报告，先解决"手工对比快照"的效率问题，不产生任何补丁。
2. **第二步**：期望清单 schema 与 L2 契约校验，打通 P1 新增必填项检测（最高价值的安全场景）。
3. **第三步**：打分匹配 + P3/P2 补丁建议 + 双向离线回演，在 mocksite 补三类漂移夹具后再开启。
4. **第四步**：数据/结构双层指纹降噪与 L3 画像（有多脚本共享需求时才做）。
每一步独立可上线、可回退，且全程不改变现有失败语义与状态机。
